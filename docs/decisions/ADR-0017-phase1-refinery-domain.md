# ADR-0017: Phase 1A Refinery Domain Foundation

**Status:** Accepted for Phase 1A foundation
**Date:** 2026-08-19

## Context

Phase 0 freezes the append-oriented persistence and the minimum provenance
chain. Phase 1 needs a durable boundary between normalized candidate claims,
resolution, confidence, and publication. A mutable `ResolvedClaim` would make
replays and audits ambiguous, while a candidate group alone cannot explain
which claims or evidence a resolver actually used.

## Decision

1. `ClaimGroup` is the normalized comparison slot. It stores a canonical
   statement, subject, predicate, qualifiers, and temporal scope while keeping
   `canonical_key` and `name` for compatibility. The default key describes the
   comparison slot and does not include object/value.
2. `ResolutionDecision` is an immutable result of the resolve stage. It uses
   only the canonical five statuses: `resolved`, `unresolved`, `conflicting`,
   `insufficient_evidence`, and `historical_change`. Deprecated Phase 0 values
   remain readable but are not generated by Phase 1 writes.
3. `ResolutionClaimInput` and `ResolutionEvidenceInput` are explicit,
   foreign-keyed provenance relations. They distinguish supporting,
   contradicting, qualifying, and rejected inputs from the broader candidate
   set.
4. `ConfidenceAssessment` is a separate immutable result. It stores the six
   required components, contradiction penalty, optional publish cap, evidence
   floor, authoritative score, policy version, and structured reasons.
5. `SourceDependency` becomes a first-class domain object with an explicit
   relation type, dependency group, independence score, reason, and signals.
6. `KnowledgeAtom` carries publication state (`active` or `withheld`) and
   semantic fields. An active atom must reference a resolved claim with a
   non-null matching confidence. Legacy atoms migrate to `withheld`.
7. A Phase 1 final `ResolvedClaim` links both its `ResolutionDecision` and
   `ConfidenceAssessment`; cross-object group, status, statement, decision,
   and score consistency is checked by the repository. Legacy rows may keep
   both links null.

## Alternatives considered

- **Update an immutable `ResolvedClaim` after confidence:** rejected because it
  overwrites a historical result and breaks exact replay semantics.
- **Generic `entity_type/entity_id` provenance:** rejected because it removes
  database foreign-key integrity and makes broken links hard to detect.
- **Only retain ClaimGroup provenance:** rejected because candidate membership
  does not show which claims/evidence were accepted or rejected.
- **Store confidence only as JSON/blob:** rejected because components and
  bounds need queryable columns and database checks.
- **Introduce a large ontology/RDF/graph database:** rejected for Phase 1A;
  the normalized slot and explicit relational links are sufficient.

## Consequences

The foundation is more explicit and replayable, and a provenance query can
separate candidates from resolver inputs. It intentionally does not implement
confidence weights, semantic extraction, or resolver algorithms; those belong
to later Phase 1 stages and fixtures.
